# LightningTrader4000 v2.00.0 Platform Upgrade Handoff

## A. Architecture Changes

### Scope decision

This pass followed the discovery audit’s recommended order and intentionally avoided a giant rewrite. The implemented slice touched all requested v2 fronts while keeping the existing workstation intact:

1. Add a lightweight shared runtime owner instead of leaving refresh ownership scattered across `stock_gui.py`.
2. Replace the ad hoc add-stock path with a persisted staged onboarding pipeline.
3. Wrap the current tabular baseline in a stable model abstraction instead of replacing it.
4. Upgrade the news system into an explicit layered runtime summary with deterministic routing plus optional richer-scoring hooks.
5. Thread onboarding/runtime/news state into readiness and trader-facing surfaces without weakening deployment truthfulness.

### Refactoring from GUI-owned orchestration into shared runtime ownership

New module: `/Users/quinnesser/IdeaProjects/LightningTrader4000/data_hub.py`

`DataHub` is a lightweight shared runtime wrapper around the existing file-backed stack. It is not a distributed service and does not try to replace `data_fetch.py`, `news_pipeline.py`, or readiness persistence. It centralizes:

- symbol refresh ownership
- per-symbol runtime bundle caching
- per-symbol freshness snapshots
- refresh-state bookkeeping
- symbol-scoped locking during refresh
- callback fanout hooks for future subscriber/event-driven use

Key methods:

- `subscribe(symbol, callback)` / `unsubscribe(symbol, token)`
- `get_runtime_bundle(symbol, allow_stale=True)`
- `get_runtime_state(symbol)`
- `store_runtime_bundle(...)`
- `refresh_symbol(symbol, force=False, reason=None, load_models=True)`
- `get_data_hub()`

Current `DataHub` refresh flow:

1. Check cache TTL.
2. Acquire per-symbol lock.
3. Refresh prices via `update_price_data`.
4. Reuse or rebuild model runtime via `model_zoo.build_model_runtime`.
5. Rehydrate support data via `refresh_support_data` if not already attached to the dataframe.
6. Compute `news_health` and `news_runtime`.
7. Compute `deployment_meta` via `summarize_deployment_readiness`.
8. Persist a consolidated bundle in-memory and expose a freshness snapshot.

This moved runtime ownership out of the GUI for the most important refresh paths without deleting existing file-backed behavior.

### Per-stock workspaces now route more through shared seams

Primary integration file: `/Users/quinnesser/IdeaProjects/LightningTrader4000/stock_gui.py`

The GUI is still the main Tkinter shell, but it now routes substantially more through the new seams:

- `self.data_hub = get_data_hub()` in `LightningGUI.__init__`
- `_runtime_bundle()` now prefers `DataHub`
- `_refresh_symbol_runtime()` uses `DataHub.refresh_symbol()` as the default path
- `_open_add_stock_dialog()` now starts the staged onboarding pipeline instead of dropping into an ad hoc training path
- `_queue_onboarding_job()` manages persisted per-symbol onboarding progress, workspace notes, refresh-on-complete, and active-workspace updates
- `reload_once_threaded()` now refreshes through the runtime layer
- `background_loop()` now refreshes through the runtime layer
- `retrain_once()` now uses the staged pipeline rather than a one-off direct trainer path
- `_workspace_summary_text()` now surfaces deployment stage, model summary, freshness state, and onboarding state
- `_initial_model_waiter()` and overview loading paths use the centralized runtime refresh helper

What still remains monolithic:

- `stock_gui.py` is still a large Tkinter orchestration file.
- The dashboard build path still fans through the GUI-driven prediction cycle.
- `DataHub` is a shared in-process runtime wrapper, not a true subscription-driven event bus.
- The workstation still uses a general `ThreadPoolExecutor(max_workers=2)` rather than a typed job queue.

## B. News-System Changes

### Layered news architecture now in place

Primary file: `/Users/quinnesser/IdeaProjects/LightningTrader4000/news_pipeline.py`

This pass preserved the heuristic-first system but turned it into an explicit layered architecture.

#### Layer A: deterministic routing

Implemented via `build_news_runtime_summary(...)` and existing relevance logic.

Inputs:

- headline rows already produced by the current pipeline
- per-symbol instrument profile
- existing scope/theme routing
- existing relevance/impact fields

Outputs:

- `profile`
- `health`
- `layer_a.scope_counts`
- `layer_a.theme_counts`
- `layer_a.top_scope`
- `layer_a.top_item`
- `layer_a.high_impact_count`
- `layer_a.summary`
- `layer_a.items`

Layer A remains always-on and cheap. It is deterministic and depends on:

- symbol aliases
- sector/theme weights
- ETF vs equity profile distinctions
- scope taxonomy already established in the prior pass

#### Layer B: optional richer scoring hooks

Also in `news_pipeline.py`

Added registry:

- `register_optional_news_scorer(name, scorer)`
- `unregister_optional_news_scorer(name)`
- `list_optional_news_scorers()`

`build_news_runtime_summary()` now evaluates optional scorers only against the top-ranked candidate headlines and returns:

- `layer_b.status`
- `layer_b.available_scorers`
- `layer_b.scored_count`
- `layer_b.results`

No heavy NLP model was added by default in this pass. That was deliberate. The seam now exists so a future pass can add a local scorer without forcing the workstation to process every headline through a slow model path.

### Stock-profile-aware relevance routing

The layered summary now exposes profile-aware context:

- `instrument_kind`
- `sector`
- `industry`
- `macro_sensitivity`
- `regulatory_sensitivity`
- `news_theme_weights`
- `context_daily_symbols`

This is now consumed by:

- `advisory_engine.py`
- `trader_analytics.py`
- workspace summary surfaces indirectly via runtime/deployment state

### What remains heuristic or crude

- There is still no entity-linking ML model.
- There is still no default FinBERT/finance classifier.
- Layer B is a hook surface, not a populated model stack yet.
- Source breadth is unchanged in this pass; the routing got better, but the provider architecture did not become a new streaming news service.

## D. Performance / Smoothness Decisions

### Decisions made to keep the app smooth

1. `DataHub` uses per-symbol locks instead of broad global refresh locking.
2. Runtime bundles are cached with TTL instead of rebuilding every symbol path every time.
3. The GUI uses the runtime bundle path first, then falls back only if needed.
4. The background loop now uses the shared runtime refresh seam rather than repeating raw fetch/model orchestration inline.
5. Overview loading and startup loading reuse the runtime refresh helper instead of building separate fetch paths.
6. UI-facing dataframe storage still trims to the bounded UI window.
7. Onboarding runs in the existing executor and persists progress, avoiding main-thread blocking.

### Cache / lazy / fanout decisions

- `DataHub` is in-memory and intentionally lightweight.
- Cache TTLs are short enough to keep refresh responsive, but long enough to avoid immediate duplicate refresh churn.
- Refresh ownership is centralized without introducing a new external service.
- Fanout exists via subscriber callbacks, but the GUI is still mostly pull-driven. That was an intentional halfway step to avoid destabilizing the workstation.

### Remaining scaling risks

- `stock_gui.py` still contains a large amount of presentation and orchestration logic even though the refresh ownership is cleaner.
- `DataHub.snapshot_symbols(...)` prefetches sequentially; it reduces duplicated GUI logic, but it is not yet a full batch scheduler.
- The workstation still computes overview forecasts inside the GUI process; the main improvement in this pass was that the overview path now pulls warmed multi-symbol bundles from `DataHub` instead of rebuilding its own symbol refresh flow.
- File-backed persistence remains the source of truth, so very high symbol counts will still eventually want more explicit caching/indexing on top of the current JSON/CSV layout.

## Addendum: v2 Tightening Pass

This follow-up tightening pass kept the same v2 direction and focused on making the new seams richer and more honest rather than broader.

### Shared runtime layer additions

`data_hub.py` now also provides:

- component-level support-state aggregation across `news`, `context`, `macro`, `event`, `options`, `breadth`, and `catalyst`
- bundle age tracking on returned runtime bundles
- `invalidate_symbol(...)` for explicit cache invalidation without restarting the app
- `snapshot_symbols(...)` for bounded multi-symbol runtime reads/prefetches

The GUI overview now uses `snapshot_symbols(...)` so the tabular multi-stock view is pulling through the shared runtime seam instead of repeating its own fetch-or-refresh loop for every open symbol.

### Onboarding evidence additions

`onboarding_jobs.py` now persists richer staged artifacts and milestones:

- `profile`
- `market_data`
- `feature_readiness`
- `model_runtime`
- `calibration`
- `readiness`
- `deployment_evidence`
- `workspace_status`

It also now includes an explicit `capture_deployment_evidence` stage and stores:

- `milestones`
- `artifacts`
- `completion_flags`
- `workspace_registered`

This makes the onboarding pipeline materially more useful to later reasoning passes because the symbol’s staged history now explains what was actually built instead of only reporting the last status string.

### Readiness / evidence integration additions

`readiness_tracker.py` now consumes the richer onboarding summary more explicitly:

- onboarding checklist detail includes artifact depth and honest/incomplete status
- deployment evidence includes `onboarding_artifacts`
- missing-evidence and next-requirements outputs now distinguish a completed pipeline with incomplete milestone capture from a truly healthy completed onboarding path

### Model abstraction additions

`model_zoo.py` now includes:

- explicit `MODE_SPECS`
- `get_mode_spec(...)`
- `list_mode_specs(...)`
- `build_inference_payload(...)`

This keeps the current tabular baseline intact but gives the platform a clearer per-mode runtime contract that future model families can implement without leaking more mode assumptions across the stack.

### News-layer additions

`news_pipeline.py` now enriches the layered runtime output with:

- `profile.profile_exposures`
- `layer_a.scope_leaderboard`
- Layer B candidate scoring metadata (`candidate_budget`, `candidate_count`, `candidates`)

This does not add a slow default ML pass. It adds a better selection seam for optional richer scoring so future work can batch only the most relevant headlines for the current symbol profile.

### GUI/runtime integration additions

`stock_gui.py` now binds the active workspace to `DataHub` subscription fanout:

- the active workspace keeps its local runtime cache warm from shared bundle updates
- the overview path uses `DataHub` multi-symbol snapshots
- overview status rows now include deployment stage context in addition to model readiness

This is still not a full event-driven workstation, but it meaningfully reduces GUI-owned refresh bookkeeping and makes the current shared runtime seam operational, not just conceptual.

- `stock_gui.py` still owns a lot of post-refresh application logic.
- `DataHub` is not yet the universal owner of every support-data path in the repo.
- Subscriber fanout exists but is not yet broadly used, so some consumers are still polling-oriented.
- File-backed persistence churn still exists under heavy multi-symbol retrain/onboarding use.
- The Tkinter dashboard remains a large single-window composition with expensive downstream analytics if symbol count grows aggressively.
